## Deviations from the brief (decided and disclosed)

- **scada-core is plain Java 21 (JDK only), not Spring Boot**: Maven Central was unreachable in the build sandbox. Virtual threads are used. Moving to Spring is a packaging change, not an architecture change.
- **SQLite stands in for PostgreSQL/TimescaleDB**; the CIM store is file-based versioned JSON. No NATS/Kafka: the log is a custom HMAC-chained file with HTTP replication.
- **Docker/Kubernetes could not be run here**; no Helm/compose is claimed as tested.
- Tokens are HMAC-SHA256 with a shared secret by default (verified identically in 4 languages). With `GS_ASYM=1` (item 19) they are Ed25519 per-service keys with role caps; the default dev stack still uses the shared secret.

## Gap list: prototype vs certifiable production

Functional (not built; N-2, short circuit, DC OPF/SCOPF, security enhancement, TCM, forecasting, AGC, DSA and outage scheduler, log/handover/comms and load-shed support done, see above): ICCP/TASE.2, IEC 61850 MMS gateway, classic OPC (DNP3, C37.118 and a reduced read-only OPC UA server exist, see above); AC-OPF (reactive/voltage), corrective SCOPF, outage scheduler, DTS/training simulator, ADMS/load-shed, web replica, CIM merge/diff/approval workflow, IEC 61970-552 full export (partial profile only), legacy importers and parallel-run mode, GIS base map (schematic layout only), shift handover/operator log, comms-loss staleness detection.

Scale/performance (item 17 closed the cold-start and bad-data parts, see Scale-hardening limits); full N-1 at 10k buses is ~700-1,400 s on one host (the distributed mode exists, but its speed-up at that size has NOT been measured, see Distributed-analysis limits); no measured ingest at 20 lakh points; no 10-year historian test (PostgreSQL write rate measured on 2 cores only, see Historian storage benchmark); IEC 104 stack self-verified only (no third-party conformance tool); latency measured on one host.

Resilience: quorum election and fencing exist for 3+ nodes (see Resilience and identity limits), 2-node pairs can still split the brain; the UI needs an external load balancer to follow failover; no geo-redundant site; the 7-day soak harness exists (`tools/soak.py`) but has only run for minutes; no chaos suite beyond the failover and quorum tests.

Security: mTLS on the field links and (optionally) the core-to-core links only (other service links not wrapped), no HSM, signed updates, reproducible builds, IDS; fuzzing, SAST/DAST and the SBOM now exist as first-party tooling (item 21) but are short, partial and self-run; dev credentials only; secrets via env or files; no third-party VAPT or source audit yet. N-1 ratings in the demo model are synthetic, so severity numbers are illustrative.

UX: no formal usability study has been run (the harness `tools/usability.py` and the task script exist, with SUS in English and Hindi, but there are no participants and therefore no results); only automated checks. The Hindi SUS wording is our own translation and has not been validated.

Security-enhancement limits: thermal overloads only (no voltage/stability remedies); switching is line-opening only; DC-model plan, accepted only after AC re-check; islanding outages are reported, not remedied; ratings are synthetic so absolute numbers are illustrative; not improved on the tiled 1,062-bus case (all 513 critical outages unchanged); plan is advisory and never executed. Test note: e2e_core's clean-data bad-data check failed twice on a long-running stack (LNR removed 3 Q-injection measurements though chi-square passed) and passed 34/34 on a fresh stack; likely measurement-noise dependent, not yet root-caused.

TCM limits: thermal and voltage-band limits only (no angle/transient stability or voltage-collapse limit, so not a certified TTC); corridors are auto-partitioned areas, not utility-defined interfaces (explicit source/sink sets are supported by the API, not the UI); transfer is by proportional generation headroom/ramp-down only; AC N-1 covers the 12 most critical outages per corridor; the DC step compares MW with MVA ratings; constraints already violated at t=0 are excluded and counted (hundreds on IEEE-118 because ratings are synthetic); margins on IEEE-118 are 0 to 15 MW for the same reason; no continuous scheduling or trend of ATC yet (on-demand with live data).

Forecasting limits: all accuracy numbers are on SYNTHETIC series (demo series SYN.LOAD.P / SYN.SOLAR.P / SYN.WIND.P are seeded by tools/seed_history.py and clearly named); real utility load will need its own backtest before any claim. No weather, irradiance, holiday or calendar inputs; intervals are marginal per horizon, assume residuals stay stationary between validation and use, and under-cover when the volatility regime shifts (wind at 6 h: 80 % interval covered 0.64 to 0.88 across runs). Wind shows no skill over persistence on the synthetic process (persistence is chosen and reported). With under 48 h of history no daily pattern is learned and the screen says so. The live total-load option needs at least 120 samples at the chosen step. The AI switch is global (all current and future AI/ML features must call `/api/ai/use`); the UI shows the toggle only to administrators, and the browser e2e flips it through the API because its operator session cannot. e2e_core's 'SE cycle ran after injection' is timing-sensitive and failed once in four runs (passed on rerun); bad-data clean-run flake noted above remains unexplained.

AGC limits: this is a SIMULATION and regulation-dispatch calculation; nothing is sent to any unit (a real AGC loop needs the secured setpoint path, unit-level telemetry validation and operator-approved modes). The CIM model carries no dynamic data, so inertia (H=5 s), droop (5 %), governor/turbine time constants, damping and ramp rates are synthetic defaults, overridable per request. Areas are coherent blocks tied by the DC network (no losses, voltage, reheat/hydro detail, no under-frequency load shedding, no CPS1/CPS2/BAAL scoring; ACE statistics only). With weak machine damping the lumped model shows a fast inter-area mode destabilised by the lagged governors for 4+ areas on IEEE-118; machine damping (1.0 pu) and the 0.03 Hz governor dead band are therefore defaults, and any run that still oscillates is flagged `oscillatory_unstable` and marked not credible. Ramp-limited AGC (3 %/min) does not settle ACE inside 600 s in 3 of 8 benchmark cases. e2e_core's SE-cycle wait was lengthened from 90 s to 150 s after the EMS cycle (now with N-2) occasionally overran it.

DSA limits: classical generator model only (constant voltage behind x'd; no exciters, PSS, governors, saturation or flux decay), constant-impedance loads, bolted three-phase faults, optional tripping of the most loaded incident line (never a bridge), no protection or reclosing; inertia (H=5 s), x'd (0.3 pu), damping (2 pu) are synthetic defaults because the model carries none. Because damping comes only from that synthetic coefficient, every electromechanical mode of IEEE-118 is below the 5 % warning line (lowest 0.9 %), so the small-signal verdict 'poorly damped' is a property of the simplified model, not a finding about any real system. Voltage margin is a lower bound within the 0.1 % step tolerance and ignores OLTC action, dynamic loads and over-excitation limiters beyond steady-state Q limits. The transient screen assesses the first 150 buses by default (all 118 in the benchmark); on the 1,062-bus tiled case it costs about 0.9 s per fault (dense Kron reduction), so a full screen would take roughly 17 min; it is not parallelised. Not validated against any commercial dynamic simulator or real event record. e2e_core's clean-data bad-data check failed again (LNR removed PF:BR0020 and QINJ:Busbar 26); QINJ at Busbar 26 is the same measurement flagged in the earlier unexplained failure, and field_sim solves with generator Q limits enforced while the estimator does not, a plausible but unverified cause.

Outage-scheduler limits: the CIM models carry only breakers, so isolation is breaker-only (no isolators, earth switches, permits-to-work, synchro-check or protection settings); a plan's manual field steps are listed, not verified; plans are advisory and are never executed from the screen (normal select-before-operate path); the study treats breaker-isolated equipment as out of service and runs a full AC N-1 twice (about 3 to 4.5 s on IEEE-118, estimated about 64 s at 1,062 buses, not measured end to end because no node-breaker CIM exists for tiled cases); ratings are synthetic. Disclosed correction: an earlier voltage check flagged 1.0500000x pu as a violation (float noise at the limit), which wrongly made many studies 'unsafe'; a 1e-4 pu tolerance (same as TCM) fixed it and exposed that the first unit-test conflict pair (BR0001/BR0015) was an artefact, replaced by a genuine islanding pair. Also fixed: the replication allow-list lacked the OUT record kind, so standbys ignored outages until e2e_core caught it. Shows 'unavailable' if the EMS cannot be reached.

Log, handover and communications limits: staleness is decided by the link, not by data age. The FEP reports a lost outstation link at once, and a silent FEP is detected by a missing heartbeat (5 s interval, 20 s timeout, configurable GS_HB_TIMEOUT_MS); outstations that report by exception cannot be told apart from a quiet point by data age, so age is deliberately not used (a half-open link that still passes keep-alives would not be caught). Stale values stay in the database with the last good value; a limit alarm that was active when data went stale stays active. Per-substation alarm threshold is 80 % stale (recovery below 20 %); a single dead point therefore raises nothing and is visible only in the comms table. Losing a shared link raises one alarm per substation (118 here) but marks the first as first-out and the rest as consequential; a real deployment would also want a single higher-level FEP alarm. After the FEP loses a core node for 4 retries it resynchronises by general interrogation when the node returns. The log is free text from authenticated operators: no attachments, no retention policy beyond 100,000 entries in memory (the event log keeps everything), no digital signature per entry beyond the HMAC chain, and no locking of an entry being amended. Handover acceptance proves a second login accepted it, not that the person read it. Fixed during this item: a general interrogation that arrived before the first heartbeat was re-staled by the feed-lost sweep (any authenticated ingest batch now counts as proof of life). Measured API latency is a flat 44 ms for every call including trivial ones, which looks like a loopback delayed-ACK artefact of the test client and server pair rather than server work (not verified); in-process engine cost is in docs/BENCHMARKS.md.

Load-shed limits: the dynamics are synthetic (the CIM carries none): inertia constant 5 s, droop 5 %, governor 0.2 s, turbine 0.5 s, 0.03 Hz dead band and a spinning-reserve cap of 5 % of online capacity, all overridable and echoed in the result; the relay stage table (49.2/49.0/48.8/48.6 Hz, 5/7/8/10 %) is ILLUSTRATIVE and not the Indian Grid Code or any utility table; one aggregate frequency, no inter-area swings, no df/dt relays, no voltage-dependent load, no islanding, no secondary control within the 60 s window. On IEEE-118 the largest-unit loss ends at 49.47 Hz with the 5 % reserve cap, which the default 49.5 Hz limit marks as outside limits; that is a property of the assumed reserve, not a finding about any grid. The 25 % loss without shedding falls to 47.2 Hz in this model, which is below any real unit trip limit, so the without-shedding curve beyond about 48 Hz should be read as 'collapse', not as a prediction. Priority classes are a deterministic synthetic hash (8 % critical, 17 % essential, 40 % commercial, 35 % residential) unless the caller supplies the utility's own; a CIM load is one sheddable block and there is no feeder or distribution topology, so this is load-shed SUPPORT and not an ADMS (no distribution network model, fault location, volt/var control or restoration switching). The roster is network-aware only through a check: at 118 buses 8 of 12 rotating periods leave new overloads after 4 re-picks (the static plan had none), and at 1,062 buses 12 of 12 periods flag overloads for both plans, so the planner trades network security for fairness and the user must read the per-period check; it does not optimise placement. The AC check reduces generation pro rata by the deficit and lets the slack absorb the rest. Nothing is sent to any relay, breaker or command path.

DTS limits: AC power flow only, the slack absorbs every imbalance, so there is no frequency, governor or protection dynamics and no relay misoperation; no SCADA telemetry, alarm or tag layer is simulated, so a trainee practises the decisions, not the operator console; sessions live in the EMS process memory (50 at most, 2 h), are lost on restart and are not shared between trainees or with an instructor view; scenarios authored by engineers are also in memory only; the score is a documented training aid with fixed weights, not a qualification, and rewards security time and a secure end state rather than the best possible plan. Fixed during this item: the N-1 endpoint hung under load because it forked a worker pool from a threaded process (the deadlock noted earlier); it now uses a clean forkserver pool, 186 cases take about 1.1 s on IEEE-118.

Model-exchange limits: the CIMXML is NOT a certified CGMES/552 profile serialisation. It uses CIM16 class and property names with SI units where a standard property exists, and a `gs:` extension namespace (http://gridsovereign.invalid/cim-ext#) for values with no standard home and for exact per-unit originals; it is not validated against the CIM RDFS schema, has no full-model dependency or supersedes chain, and has not been exchanged with any third-party CIM tool (the round trip is tested only against this implementation). Importing standard properties alone is tested (SI values recover the per-unit model to 1e-9), but equipment this prototype does not model (three-winding transformers, DC, measurements, topology profile, SV profile) is ignored on import. The XML parser handles the 5 predefined entities and numeric references only (no DTD, CDATA, external entities); it is hand-written and fuzzed for panics with 400 mutations, not with a coverage-guided fuzzer. The PSS/E RAW reader is written from the published v33 record layout and tested on text generated by `tools/mk_legacy.py` from the public pypower cases, so it proves the reading of the layout, NOT compatibility with real planning-tool exports; three-winding transformers, switched shunts, DC lines, areas and zones are refused or ignored (stated in the import warnings). The pypower copy of case 14 carries no base kV, so 138 kV is assumed in the generated files. Imported models get one substation per bus in region "Imported" with no coordinates, no ratings unless the file has them, and no voltage-level limits. Parallel-run limits: the mode switch is replicated and audited, but the comparison itself lives in memory on the node that received the samples (lost on restart, not shared with the standby); it compares at the instant a sample arrives against the current value, with no time alignment, scan-rate compensation or quality-code mapping; tolerances are the caller's choice (defaults 0.5 absolute plus 0.5 % relative are placeholders, not a standard); the agreement figure is a measurement, not a cut-over approval. Nothing here ingests a legacy protocol feed directly: samples arrive as JSON.

Scale-hardening limits: tested on SYNTHETIC networks made by tiling IEEE-118 with synthetic tie lines, not on a real 10k-bus utility model. The Levenberg-Marquardt fallback is slow (5.6 s at 10,030 buses) and is a last resort; a case beyond the loadability limit is reported as not converged (tested), never as a result. Above 3,000 states the normalized residual is computed only for the 60 measurements with the largest weighted raw residual, so it is exact for those but can miss a bad measurement whose raw residual is hidden by leverage; the response says which method ran (`rn_method`). The Bonferroni local test is a statistical rule with alpha = 0.01 per run (0 false removals in 4 clean 5,074-bus runs, which is a small sample), not a certified detection guarantee. Bad data in critical measurements (zero redundancy) is still unidentifiable by any residual method.

Distributed-analysis limits: all peers in the test and benchmark run on ONE machine, so the live run shows correctness and fault tolerance, not speed-up: on IEEE-118 N-1 (186 cases) it took 5.4 s on one process and 10.3 s over three, because every shard rebuilds the network and solves the base case again and the processes compete for the same cores. A speed-up needs peers on separate hosts and a model large enough that the cases cost more than that fixed per-shard overhead; that has not been measured here. Peers are trusted to the extent of the shared HMAC secret (no mTLS between EMS processes yet, item 19), a peer that returns plausible but wrong numbers for the right digest is not detected (no redundant execution or sampling check), the shard payload carries the caller's token, shards are statically dealt (no work stealing) and the coordinator is a single point of failure for a request. Distributed N-2 is refused on a network split into islands by the switch overlay.

Resilience and identity limits (item 19): the quorum protocol is Raft-style but is NOT Raft: operator-record replication is still best-effort, a candidate's vote does not check log completeness, so a leader change can lose records the old leader had not yet replicated; the lease assumes bounded clock drift between nodes; the fencing term is kept only in memory at the FEP (a restarted FEP accepts any term until it sees one); two-node deployments still run in pair mode and can split the brain. Not tested under real network partitions between hosts (all nodes are processes on one machine; partitions are simulated in unit tests and by killing processes). Asymmetric tokens: private keys are plain files (0600), no HSM, no rotation workflow beyond issuing a new key id and trust list, the cores share one key class that signs both peer identities and user logins, and the outstation simulator uses a static token. The Java core still needs a shared secret for its audit key. mTLS covers only the core-to-core links (through a loopback proxy); the other service links (FEP, EMS, historian, cim-pds) are not wrapped yet, the services keep their plain loopback ports so a local process can bypass the proxy (production needs the plain ports bound to a Unix socket or firewalled), and the proxy-to-service hop is plaintext on loopback. The development PKI has no OCSP and the CRL is a file. Not a certified design; no third-party review.
State-estimator note (found while running item 19 and traced to its cause in item 22): the clean-data check in `e2e_core` kept failing on live data with a 9-10 sigma normalised residual at one generator bus (Busbar 26). Cause: the core built each bus-injection measurement from generator and load meters but gave it a sigma computed from the NET value, ignoring that (a) the component meters' noise adds up even when they cancel and (b) report-by-exception sends a value only after it moved by 0.2 % of range, so a held value is stale by up to about 2 MVAr on a +-1000 MVAr generator. That is a modelling error in the estimator's input weights, not simulator noise. Fixed in `EmsLink.java`: sigma now uses the root-sum-square of the component magnitudes plus the dead-band uncertainty (range x `GS_DEADBAND`, default 0.002, equal to the outstation simulator's default; set it to match the real RTUs). The earlier workaround (a floor of 8 sigma on the local test) is still in place and is not the fix. After the fix `e2e_core` passes 78/78 on a fresh stack in the final run.
Found and fixed by re-running older suites: the core sent `X-Fence-Term: 0` in pair/single mode and the FEP refused every command (`e2e_secure` failed 4 checks); the core now sends the header only in quorum mode. The leader reported its peers as down in quorum mode (the `alive` flag was updated only by the pair-mode probe); fixed.

Historian / bus / deployment limits (item 20): TimescaleDB was NOT available here, so the hypertable path is untested (tests ran on plain PostgreSQL 16.15). PostgreSQL writes are first-write-wins (a re-sent row with a different value is ignored; the SQLite store overwrites). The bus is Redis Streams, not Kafka or NATS; the Java publisher has no TLS and no reconnect of the consumer position beyond the stream itself, Redis here ran without persistence in the tests (an outage loses stream contents, the core re-sends everything changed since its last successful publish, which covered the gap in `e2e_bus`), and only the leader publishes, so a leader change sends a full snapshot (consumers must tolerate repeats; the stores do). Bus delivery latency from core to historian and bus throughput were not measured. Compose file, Dockerfiles and Helm chart were never run: no container runtime and no `helm` in the build environment, only YAML parsing and a template-balance check (see `deploy/README.md`). No high availability for PostgreSQL or Redis is provided; the chart expects managed services.

Security-testing limits (item 21): the fuzzers are short and, except for Go's native engine, not coverage-guided (no `cargo-fuzz`/nightly and no AFL/libFuzzer here); a clean run means no panic in those minutes, not absence of bugs; the Python services were fuzzed only through the HTTP API (DAST), not at function level. The DAST script is our own and covers what we thought of; it is not OWASP ZAP/Burp and not an independent penetration test (a CERT-In empanelled VAPT is still needed). SAST is clippy/bandit/go vet plus grep rules; `staticcheck`, `gosec`, `semgrep` and `cargo audit` could not be installed (no Go proxy, no rule registry here). `npm audit` and `pip-audit` found nothing, which only means nothing is in their databases today. Real defects found and fixed by this item: upper-case hex accepted in the signature of shared-secret tokens (Rust and Go; Java and Python were already strict), `RwLock` poisoning could turn one panic into permanent failure of cim-pds (23 `unwrap()` calls), EMS returned 500 and reset the connection for a model id with a control character, unknown `/api/` routes returned the web app with HTTP 200, the historian silently defaulted to a file in `/tmp`, an `assert` was used for control flow in the distributed runner, and psycopg (LGPL) had to be replaced.
Soak limits: nothing here ran for 7 days. The harness was exercised for 8 minutes and 3 minutes only (about 280 workload calls, 0 failures, all services healthy); over that time the JVM and EMS memory grew as heaps fill, which the detector correctly calls inconclusive (it refuses to call a leak before 2 h after warm-up). The 7-day run is started with `nohup tools/soak.py --hours 168 &` on the target host and judged with `--analyze`. The harness has no fault injection (killing nodes during the soak is done by `e2e_failover`/`e2e_quorum`, not here) and the workload is light (a few calls per 5-30 s on top of the simulated telemetry).

## What stands between this prototype and a certified, deployable system (final gap list)

1. **Independent assurance (not started)**: CERT-In-empanelled VAPT of the running system; an independent source-code audit of the security envelope (token handling, command authorisation, audit chain, mTLS proxy, PKI tool); IEC 62443-4-1 process and 62443-3-3 / 4-2 technical gap assessment; reproducible, signed builds and signed updates; HSM-backed keys and an enterprise CA instead of the development PKI.
2. **Protocol conformance (not started)**: tests against third-party master/outstation stacks and the IEC / DNP3 Users Group test suites for 104, 101 and DNP3; a byte-exact comparison of the C37.118 frames with the standard and a real PMU; IEC 62351-5 wire-compatible authentication; ICCP/TASE.2 and IEC 61850 MMS do not exist, and the OPC UA server is a reduced, unsecured, read-only one.
3. **Real data (not started)**: all models are IEEE or synthetic; ratings, dynamic parameters, costs, load-shed tables and relay settings are illustrative. A utility model, real RTU telemetry and real forecasts are needed before any number here can be used for a decision.
4. **Operations at scale (partly measured)**: nothing has run for 7 days; no measured ingest at 20 lakh points; no 10-year historian; the Raft-like election lacks log-completeness checks; compose and Helm files were never run; geo-redundancy and a chaos suite do not exist.
5. **Human factors (not started)**: usability study with real dispatchers in English and Hindi; independent accessibility audit with assistive technology; operator training and procedure documentation.
6. **Regulatory and procurement fit (unknown)**: the EOI's own scoring criteria, grid-code specifics (Indian Grid Code UFLS tables, scheduling, ABT/DSM interfaces) and data-localisation and audit rules need a read of the actual documents; none were available here.

## Roadmap to a pilot

1. **Foundations (hardening)**: Postgres/Timescale + message bus, mTLS/asymmetric tokens, quorum-based leader election with fencing, sparse SE inverse, robust cold-start PF, distributed N-1 with ranking.
2. **Protocol conformance**: third-party interop and conformance testing of secure 104 (62351-3/5; in-house subset built) and 101, DNP3, ICCP, 61850 gateway; test against third-party stacks/tools; fuzz all parsers.
3. **Applications**: OPF/SCOPF, short circuit, TCM, AGC, forecasting, DSA, DTS, outage scheduler, each validated against published cases.
4. **Security assurance**: secure SDLC with CycloneDX SBOM per release, SAST/DAST, then CERT-In-empanelled VAPT, followed by an independent source-code audit; IEC 62443-4-1 gap assessment.
5. **LDC pilot**: shadow/parallel-run beside the incumbent system on one SLDC (read-only first, parallel-run mode and the model import path already exist), usability study with real operators (harness exists), 7-day availability test (harness exists), then supervised control.
6. **Gate before step 5**: steps 2 and 4 (CERT-In VAPT and the independent source audit) must pass before the system is connected to any live network, even read-only.

## SBOM
`tools/sbom.py` (item 21, replaces the partial `make_sbom.py`) writes `docs/SBOM.cdx.json` (CycloneDX 1.5) and `docs/SBOM.md`: 278 components across Cargo (the release binary's normal+build graph from `cargo metadata --locked`), npm (`package-lock.json`, production and dev separated), Python (the dependency closure of both requirements files, read from the environment), Go (standard library only), Java (JDK only) and the container base images. Licences are as declared by the packages and are checked against a policy: no strong-copyleft or non-commercial licence is present; five items are flagged for review (3 font packages under OFL-1.1, axe-core and certifi under MPL-2.0; axe-core is a test tool and not shipped). Found by this check: `psycopg` (LGPL-3.0) was added for the PostgreSQL historian and was replaced by `pg8000` (BSD-3-Clause); the compose file pins Redis 7.2 because later Redis releases are no longer BSD. Limits: Python versions are what is installed here, not hash-locked; images are tags not digests; licence texts and notices were not audited; no Cargo advisory scan (`cargo audit` could not be installed offline from here).

### Secure field links: limits (item 13)

- The application-layer authentication is our own subset (S_CH/S_RP/S_ER type ids 81/82/87, a 16/22/8-byte element, HMAC-SHA256 truncated to 16 bytes, one pre-shared key per link). It is not IEC 62351-5 wire-compatible: no key-update, no aggressive mode, no per-user keys or roles in the protocol. Production needs a certified stack and interop tests.
- The TLS profile applies to IEC 104 only. IEC 101 links carry no confidentiality or authentication (as in the standard, physical protection is assumed); the serial transport opens a device file whose line settings (baud, parity) must be configured outside the program.
- IEC 101: unbalanced mode only; no balanced mode, file transfer, clock synchronisation or counter interrogation. The slave class-1 queue holds 20,000 events; beyond that the oldest is dropped and counted in `Stats.Dropped`. Tested against our own master/slave only, not against third-party devices or the IEC test suites.
- The CRL must be supplied and refreshed by operations; there is no OCSP. The dev PKI keeps the CA key on disk unencrypted.

### DNP3 and C37.118: limits (item 14, partly done)

- DNP3: objects g1v2, g2v2, g30v5, g32v7 and g12v1 only; other variations from a third-party outstation are counted (`Stats.Unsupported`) and parsing of that response stops. No unsolicited responses, no link-layer confirms, no time sync, no file transfer, no Secure Authentication (SA v5). Security relies on TLS around the stream. Point index equals the IOA; a double-point is carried as one binary input with the chatter flag marking the two indeterminate values. One outstation serves one common address. Tested only against our own master/outstation, not third-party stacks or the conformance suite.
- C37.118: single PMU per frame, floating-point formats only, TCP only, no CFG-3, no time-alignment PDC buffer. The CRC check values are from the CRC catalogues; the frame layout was written from the standard text and has NOT been compared with a byte-exact example from the standard or a real PMU. PMU values ARE now fed into the SCADA point model (item 22 leftover, see the next section).
- NOT built in item 14: ICCP/TASE.2 and IEC 61850 MMS gateway (OPC UA: reduced server, see its section).

### PMU mapping into the point model (item 14 leftover)

- What exists: `cim-pds/src/pointlist.rs` adds points for each PMU named in an overlay file (`CIM_PMU_FILE`, JSON `[{"substation","prefix","phasors":[..],"analogs":n}]`): `<prefix>.F` (Hz), `.DF` (Hz/s), `.<phasor>.MAG`, `.<phasor>.ANG` (degrees), `.A<n>`, each PMU on its own common address starting at 9001. The FEP spec `c37118://host:port#IDCODE/PREFIX@CA` (`internal/pmubridge`) connects as a PDC-style client, checks that every channel the PMU announces has a point (otherwise it forwards nothing and reports why), converts rectangular or polar phasors to magnitude and degrees, thins the stream to one value set per second (last frame wins), sets invalid / not-topical quality from the PMU status word, marks the points stale when the stream is lost and refuses commands. Tests: 4 Go tests (hand-computed conversions, quality bits, mismatch refusal, a full 50 fps stream through the bridge, race detector on), 1 Rust test, `tools/e2e_pmu.py` (13 live checks incl. loss and recovery), browser check.
- The PMU is NOT in the CIM model (our CIM subset has no PMU class); the overlay file is engineering configuration outside the model, so a model change does not move it. The magnitude unit is whatever the PMU sends (no scaling to kV or pu is applied); `pmu-sim` is SYNTHETIC and not coupled to the power flow, so the live PMU values are not compared with the state estimate. One PMU per connection (no PDC aggregation), no time alignment, no sync-quality analysis, 1 s forwarding so unsuitable for wide-area control, the frame layout is still unverified against a byte-exact standard example or a real device.
- Still NOT built: ICCP/TASE.2 and IEC 61850 MMS gateway. They need the OSI session/presentation/ACSE stack and an ASN.1 BER codec for MMS; nothing of them exists. The System health screen says so in both languages.

### OPC UA server, reduced (item 14 leftover)

- What exists (`fep-gateway/internal/opcua`, FEP flag `-opcua host:port`, stack option `GS_OPCUA=1`): a read-only OPC UA server written from the UA binary encoding: UA-TCP Hello/Acknowledge, SecureChannel with SecurityPolicy None, anonymous sessions, services GetEndpoints, FindServers, CreateSession, ActivateSession, CloseSession, Read and Browse. The address space is built from the model's point list: `Objects/GridSovereign/<substation>/<tag>`, Double for analogs, Int32 for double-point states, UA status Good / Uncertain (stale or not topical) / Bad from the point quality, source timestamp from the field. The FEP keeps the latest value of every point for this (a live cache) and marks cached values uncertain when an outstation link is lost. Responses larger than the client's buffer are split into chunks.
- Evidence: 8 Go tests (race detector; refused policy and user-name tokens, Read before activation, quality to status-code mapping, hierarchy browse, a 3,000-reference response reassembled from chunks, 150 malformed or mutated messages), a native fuzz run of the decoders (about 1 million executions, no panic), `tools/e2e_opcua.py` (16 checks on the live stack using an independent client, asyncua, which is a test-only dependency: namespace array, browse down to the variables, 112 values compared with the SCADA core, write / method / unknown node / hostile bytes refused). Read of 1,000 variables in one call in a 14,868-point space: about 5.5 ms on loopback (test client included).
- **Limits you must keep in mind**: no message signing or encryption (SecurityPolicy None only), no user authentication (anonymous), so it must be bound to loopback or a protected segment and is NOT suitable for a hostile network; the default listener is OFF. No subscriptions or monitored items (clients must poll), no writes, no methods, no history, no continuation points (Browse returns everything), no TranslateBrowsePaths, no BrowseNext, no certificates or GDS, no discovery server registration, one session per connection, 64 sessions at most. Only the Value, DataType, ValueRank, AccessLevel, NodeClass, BrowseName, DisplayName, Description and NodeId attributes exist. The OPC UA type system is minimal (the standard ns=0 address space is NOT present beyond Root, Objects, Server and NamespaceArray), so clients that expect ServerStatus, types or the standard model will not work. Tested only with asyncua, not with UaExpert, Prosys, Milo or the OPC Foundation compliance test tool, so interoperability with other clients is unknown. This is a "reduced server", not an OPC UA product.

### Conformance, acceptance and usability (item 22): limits

- **The EOI scoring rubric (criteria, weights, the 80 % technical share) was not in the brief or the repository.** `docs/eoi_weights.csv` is an empty template; `tools/eoi_score.py` scores nothing until it is filled in. No score is claimed.
- The conformance run is self-run on the development host (2 CPUs) against our own simulators. It is regression evidence, not third-party conformance. The traceability statuses (`met`, `partial`) are our own assessment; `docs/TRACEABILITY.md` states the limit of each row.
- The usability study was **not run**. `tools/usability.py` and `docs/usability_tasks.json` are a harness (task script, SUS in English and Hindi, scoring with bootstrap and Wilson intervals); its self-test uses made-up numbers. The Hindi SUS text is our own, unvalidated translation.
- Found and fixed by running everything together for the first time: (1) `e2e_interop` failed after `e2e_core` on the same stack because the earlier suite leaves switching state behind; the runner now restarts the stack before every suite; (2) `e2e_mtls` assumed core A was the leader and judged "the leader stays" even when the killed node was the leader; it now waits for a leader among the survivors; (3) the state-estimator injection-sigma error described above; (4) one browser check (`regional-model tab lists models to combine`) failed once in four runs because it counted checkboxes before the model list had loaded; it now waits for them.
- Not re-run in the final conformance run: the 7-day soak (harness self-test only), the PostgreSQL write-rate benchmark and the other `tools/bench_*.py` benchmarks (numbers in BENCHMARKS.md are from the item they belong to, not from the final run).

### Model governance: limits (item 15)

- The model schema is the CIM subset of this prototype, not full CIM/CGMES profiles, so there is no CGMES difference-model (`dm:`) import or export; the diff is our own JSON structure. Item 16 covers the 61970-552 export.
- Merge works per class and mRID, then per field. It does not understand electrical meaning: two edits that merge cleanly can still give a bad network, which is why every merge result is validated (errors block the merge, warnings do not) and why no power-flow or security study is run at merge time.
- Approval is by named users with a role and jurisdiction in the bearer token; there is no signature on a review and the proposal log is a plain list (the model history it ends in IS hash-chained). Roles come from the shared-secret tokens (see deviations).
- Hierarchical merge unions children by mRID. It does not renumber, rename or detect that two children describe the same physical element under different mRIDs; boundary elements must carry the same mRID and content in both. The split assigns each element to the region of its first node and gives the neighbour only a copy of the far-end node, voltage level and substation.
- Snapshots are kept for the last 500 versions; a proposal whose base version has aged out cannot be merged (reported as such).
- The change list in the UI shows the first 60 field changes; the API returns all.
- One cim-pds process holds the models; models and proposals are not replicated across nodes (item 19/20).
